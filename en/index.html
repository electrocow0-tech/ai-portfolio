How I run a project

This is how product ML teams work: discovery → requirements → design doc → eval-first → staged rollout. In large companies these steps are split between an analyst, an architect, an ML engineer and a PM — I cover them myself, from the first meeting to production support.

  1. 01

    Understanding the process

    Interviews with the owner, managers and staff; an as-is process map; where money and time leak. I fix the business metric and the current baseline — otherwise there is nothing to prove the result against.

  2. 02

    Detailed spec

    Scenarios and boundaries: what the LLM does, what code does, what a human does. Escalation rules, acceptance criteria, data, API and personal-data constraints.

  3. 03

    System design

    Architecture, integrations, data model, a model choice per step, cost and latency estimates, alternatives and trade-offs. The cheapest solution that actually solves the problem.

  4. 04

    Data and eval before code

    A set of real examples with expected answers is built before development — every version of prompts, models and retrieval is compared on it.

  5. 05

    MVP and pilot

    A prototype on real data, a pilot on part of the traffic or in shadow mode, a human in the loop. Staff feedback goes into rules and prompts.

  6. 06

    Production

    CI/CD, tests and prompt regression runs, monitoring and alerts, documentation, staff onboarding.

  7. 07

    Iteration

    Error review from logs and metrics, updates to the knowledge base, rules and scenarios.

01

Industrial equipment manufacturer · Avito + Telegram

Dual-channel AI seller for a B2B manufacturer

Problem

Hundreds of SKUs, specs and price lists. First contact happens on Avito, the conversation continues in Telegram. Sales engineers drowned in routine, customers repeated themselves across channels, and evening enquiries waited until morning.

My part

Mapped the funnel with the sales team, agreed objection scenarios and handoff rules, designed the architecture and built the whole system.

What I built
  • Shared customer memory across Avito and Telegram: short history, summary, structured facts.
  • RAG over documents and price lists in Google Drive with incremental re-indexing by hash every 15 minutes.
  • A state-machine agent: qualification → product match → objections → handoff → follow-up.
  • Manager takeover that locks auto-replies and hands the dialogue back to AI mode.
Engineering decisions
  • An SKU filter in retrieval keeps search from drifting to a similar but different model.
  • No evidence in the knowledge base means no number in the reply: the question goes to a manager.
  • Idempotent CRM writes, retries with backoff, a visible error queue.
Result

Two sales channels work as one funnel 24/7, and the manager receives a lead with requirements already collected.

What it shows → Turning a sales process into a controlled system: hallucination-safe RAG, memory, human handoff, reliable integrations.

Python · FastAPI · PostgreSQL · Redis · RAG · LLM API · Pydantic · Google Drive API · Telegram · Avito API · CRM API · n8n · Docker · Grafana

02

Sales teams of 20+ people · web app

Voice AI sales trainer

Problem

Sessions with a sales coach need scheduling, new hires practise on real leads and lose them, text scripts in an LMS don't build a voice skill, and the head of sales has no time to coach everyone individually.

My part

Agreed the checklist and criterion weights with the head of sales — the same sheet used for real-call quality control. Designed and built the whole service: voice agent, scoring, user cabinet, admin panel and infrastructure.

What I built
  • The salesperson opens the cabinet and talks in real time with a virtual customer who objects, interrupts and never volunteers their needs.
  • Right after the call — a checklist review and spoken feedback “from the manager”.
  • The score and the recording go to the manager's sheet and the admin panel.
  • An AI coach reads the salesperson's history and builds the next customer around their weak spots, without repeating scenarios.
Engineering decisions
  • One checklist shared with call quality control: you can see whether a skill transfers from simulation to real calls.
  • The final score is computed in code from criterion weights; the model only answers checklist questions.
  • The page with the voice widget is served by a separate static container and the API only handles /api via Traefik: the API framework's response headers dropped the voice session within a second.
Result

A 10–20 minute session at any time, with no coach and no risk to real leads; the head of sales sees each person's progress.

What it shows → A realtime voice product from UX to infrastructure, and a training ↔ quality-control loop built on one methodology.

ElevenLabs Conversational AI · LLM API · Python · FastAPI · Traefik · Docker · Google Sheets API · web cabinet

03

Car dealership · CRM with no accessible API

Automated call quality control

Problem

An employee spent 3–4 hours a day exporting data and listening to calls, and only 20–30% of calls were reviewed. There was no CRM API access.

My part

Built a 15-criterion checklist and edge-case rules with the head of sales — iteratively, through review sessions with the client. Designed and built both loops.

What I built
  • An RPA robot collects deals and recordings from a CRM with no API: normalisation, deduplication, upsert.
  • Transcription with diarization and a manager / customer split.
  • Two LLM calls: a content-based call-type classifier and a checklist scorer.
Engineering decisions
  • The final score is computed in code, not by the model: answers snap to a “0 or criterion weight” grid.
  • Reference transcripts with expected scores are re-run on every criteria change.
Result

Every call is checked instead of a sample; data reaches analytics 1–2 minutes after the deal, and the QA employee handles only edge cases.

What it shows → Delivering where there is no API; LLM scoring you can trust; turning the client's expertise into system rules.

Python · browser RPA · PostgreSQL · AssemblyAI · LLM API · S3 · Google Sheets API · Telegram Bot API · Docker · Grafana

04

Own product · media and SMM

AI editorial team for a Telegram channel

Problem

Process a large flow of sources, keep the channel's voice, never publish unverified text, and leave the decision to a human.

My part

The product is entirely mine: from the hypothesis and an n8n prototype to a standalone Python service.

What I built
  • Collection from Telegram, RSS and a search API with deduplication on ingest.
  • Four roles — filter, copywriter, editor, critic — with a JSON contract between steps.
  • A quality gate: below 7/10 triggers a rewrite with the critic's feedback, up to 3 iterations; approval via Telegram buttons.
Engineering decisions
  • A separate model and temperature per role — an order of magnitude cheaper than one top model everywhere.
  • LLM provider switching via base URL — resilience to blocking.
Result

A daily digest with mandatory human approval, at about $100 a month to run.

What it shows → A multi-agent pipeline with quality control and practical economics; the path from a no-code prototype to a service.

Python · aiogram · APScheduler · Telethon · LLM API · n8n · PostgreSQL · Docker
